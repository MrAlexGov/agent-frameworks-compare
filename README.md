# Один агент — три фреймворка: LangGraph vs PydanticAI vs OpenAI Agents SDK

Одна и та же задача, реализованная на трёх агентных фреймворках, с одинаковыми моделью, инструментами,
промптом и схемой ответа. Цель — понять, что реально меняется при выборе фреймворка: точность, число
вызовов инструментов, задержка, объём кода.

## Задача
Ассистент вымышленного облачного провайдера «Облачко» (база знаний выдумана, чтобы модель не могла
ответить из памяти). Инструменты:
- `search_kb(query)` — поиск по базе знаний (IDF-взвешенное совпадение стемов, top-2 раздела);
- `calc(expression)` — безопасный калькулятор (AST, без `eval`).

Ответ — структурированный (`Answer`: `answer`, `value`, `sources`; Pydantic-модель), у каждого фреймворка
своим штатным механизмом: `response_format` в LangGraph, `output_type` в PydanticAI и Agents SDK.

16 задач ([common.py](common.py)): 7 одношаговых (найти факт), 9 многошаговых (найти цифры → посчитать:
скидка за год, компенсация по SLA, стоимость аренды GPU и т.п.), 2 «ловушки» (ответа в базе нет). Проверка
детерминированная: число в поле `value` (или в тексте) или обязательная фраза.

## Реализации
| Фреймворк | Файл | Строк | Как устроено |
|---|---|---|---|
| LangGraph 1.2 | [impl/langgraph_agent.py](impl/langgraph_agent.py) | 17 | `create_react_agent` + `ChatOpenAI`, `response_format=Answer` |
| PydanticAI 2.55 | [impl/pydanticai_agent.py](impl/pydanticai_agent.py) | 20 | `Agent(output_type=Answer, tools=[...])`, `OpenAIChatModel` |
| OpenAI Agents SDK 0.23 | [impl/openai_agents_sdk.py](impl/openai_agents_sdk.py) | 19 | `Agent` + `OpenAIChatCompletionsModel` поверх стороннего endpoint, трейсинг выключен |

Все три работают через любой OpenAI-совместимый endpoint (`EVAL_BASE_URL`, `EVAL_API_KEY`). В прогоне —
Kaggle Benchmarks model proxy.

## Выводы
- **Модель важнее фреймворка.** На Gemini 3 Flash все три — 100%. На GPT-5.4 nano все три ошибаются на одних
  и тех же задачах (см. ниже); разница 0.88 vs 0.94 — это 2 задачи из 32, в пределах шума.
- **Задержка различается заметно.** LangGraph — самый медленный (structured output в `create_react_agent`
  делается отдельным вызовом LLM после цикла агента: +1 запрос на каждый ответ). PydanticAI отдаёт структуру
  как «финальный инструмент» (output tool), Agents SDK — через `response_format` в том же цикле, без лишнего запроса.
- **Объём кода одинаковый** (17–20 строк): для простого ReAct-агента выбор фреймворка — вопрос экосистемы
  (LangGraph — явные графы и checkpointer'ы, PydanticAI — типизация и DI, Agents SDK — handoff'ы между агентами),
  а не «сколько писать».
- Подводный камень Agents SDK: по умолчанию шлёт трейсы в OpenAI даже при стороннем endpoint —
  нужно `set_tracing_disabled(True)`. Подводный камень своего пакета `agents/` — он перекрывает пакет SDK
  (`from agents import Agent` падает), поэтому реализации лежат в `impl/`.

## Честные оговорки
- **Ошибки nano на задаче про S3 (6 из 10 провалов) — баг моего поиска, а не модели.** Стемминг
  отбрасывал токены короче 3 символов, поэтому запрос «хранение S3» не находил раздел `s3`, и модель честно
  отвечала, что цены нет (и считала по цене снапшотов). Gemini формулировала запрос иначе и попадала.
  Исправлено (`len(w) >= 2`) после прогона; перепрогон nano — TODO (квота прокси на день исчерпана).
  Вывод тот же, что в RAG: качество retrieval-инструмента влияет на агента сильнее, чем фреймворк.
- 16 задач — маленький набор; это сравнение «на одной задаче», не общий бенчмарк фреймворков.
- Задержка измерена через прокси — абсолютные значения зависят от него, сравнивать стоит только относительно.
